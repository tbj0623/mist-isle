# tick 尖峰归因报告（1.3.0）

日期：2026-10-29 · 本机（Windows 11 / Node v24.20 / i5-11500 / 非独占机器）

## 结论先行

**`artifacts/perf-report.md` 里 tick P99 27.5ms / max 383ms 的超预算，主体是测量环境的 CPU 争抢，不是代码回归。**

证据：把「墙钟耗时」换成「进程 CPU 时间」后，同一份代码的每 tick 成本稳定在
**1.1–2.5 ms**（33.33 ms 预算的 3–8%），而墙钟 P99 在同一批运行里能在 12–133 ms 间跳。
同一个 tick 号在不同轮次里既可能是 1.3 ms 也可能是 711 ms —— 只有外部调度能造成这种差异。

但这不等于「没有优化空间」：**AI 占 tick CPU 的 94.2%**（2.81 ms vs 关掉 AI 后 0.16 ms）。
下面是我在本次会话中做的两项结构性优化，以及仍然存在的真实开销。

## 测量方法

```js
// 每个 tick 同时记录墙钟与进程 CPU（user + system）
const c0 = process.cpuUsage(); const w0 = performance.now();
match.update(1 / 30);
const wall = performance.now() - w0;
const c1 = process.cpuUsage(c0);
const cpu = (c1.user + c1.system) / 1000;   // ms
```

64 人满编（1 真人 + 63 bot）、`deployStyle: 'instant'`、3000 tick、重复 3 轮取中位数。

| 指标 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 解读 |
| --- | --- | --- | --- | --- |
| 墙钟 P50 (ms) | 1.58 | 1.33 | 1.27 | 稳定 |
| 墙钟 P95 (ms) | 29.92 | 4.02 | 3.03 | **17 倍波动** |
| 墙钟 P99 (ms) | 183.68 | 29.37 | 13.76 | **13 倍波动** |
| 墙钟 max (ms) | 484.5 | 342.0 | 188.2 | **2.6 倍波动** |
| **CPU/tick (ms)** | 2.37 | 1.52 | 1.12 | 同量级，随机器负载变化 |

关键判据：**墙钟分位的轮间倍差远大于 CPU 时间的倍差**。如果是代码问题，两者应同比恶化。

### 尖峰与周期的关系（否定假设）

我最初怀疑尖峰对齐 `tickCount % 50 === 0`（`_compactLoot` 的 loot 压实周期）。
实测 291 个 >8ms 的尖峰，按 `tickCount % 50` 分布：

## 本次尝试的优化（全部回退，原因如下）

我试了三项优化，**三项都回退了**。记录在这里是为了避免下次重做。

### ❌ `wallDistance` range 截断（尝试后回退）

动机：`findCover`（`shared/ai.mjs:845`）对 16 个方向候选点各调一次 `wallDistance`，
传入的 range 是「候选点到敌人的距离」（常见 30–70 m），而 `wallDistance` 对这条长线段
做 `grid24.gather()` + 逐障碍 slab 相交，代价与线段长度成正比。

想法：`tight = 1 - wd/dE` 在墙距 > 10 m 时已接近 1，截到 10 m 应该语义不变。

**实测证伪**：2000 个真实场景采样，**1075 个评分发生变化，且全部偏高**
（0 个偏低）。原因是 `wallDistance` 在 range 内找不到墙时返回 range 本身，
截到 10 m 后「墙在 12 m 外」的候选点也被算成贴墙紧 —— 这是**系统性偏好远墙掩体**，
不是优化。已回退，并在代码里留下注释。

### ❌ `scanEnemies` 有界插入（尝试后回退）

动机：被 64 bot × 每 0.2–0.6 s 各调一次，每次 `new []` + `push` 全部敌人 + 原生 `sort`。

**实测更慢**：CPU/tick 1.81 → 3.05 ms。V8 对「小数组 push + 原生 sort」优化极强，
而手写插入循环 + `slice(0, n)` 每次仍要分配结果数组。

### ❌ `nextThink` 首次相位错峰（尝试后回退）

动机：所有 bot 的 `nextThink` 初始值都是 0，第 1 帧 64 个 bot 同时
`scanEnemies` + A\*；之后周期又都落在 0.16–0.95 s 的相近区间，长期同相。

用 `(hash32(bot.id) % 97) / 97 * 0.9` 错峰后 CPU/tick 从 2.81 → 1.81 ms，
**但改变了 AI 的战术表现**：

| 指标 | 错峰前 | 错峰后 |
| --- | --- | --- |
| 新兵 KD | 0.20 | 0.35 |
| 新兵前 25% 队率 | 5.0% | 10.0% |
| 老兵胜率 | 66.7% | 83.3% |
| 精锐胜率 | 33.3% | 16.7% |

错峰改变了「谁先发现谁」。而三档平衡是 **120 局实测标定**出来的
（见 `shared/rules.mjs` 的 `DIFFICULTY` 注释），时序扰动会让那套结论失效。

## 为什么全部回退：测量信噪比不足

在这台**非独占机器**上，同一份代码的 CPU/tick 在 **1.1–3.2 ms** 之间随机器负载漂移
（3 次连续测量的中位数差可达 2.8 倍），而三项优化的理论收益都在 0.5–1 ms 量级 ——
**比噪声还小**。这意味着一件事：

> 在无法可靠测量的环境里，「看起来更快」的改动只是把噪声当成了信号。
> 而三项改动中有两项的**行为影响是可测的**（掩体评分系统性偏高、AI 三档胜率反转），
> 这两项都是真实的退化。

**结论：没有独占机器（或 CI 专用 runner）与稳定基线之前，不做 AI 热路径的微优化。**
真正的优化方向应该是架构级的（同队共享寻路结果、减少每帧全量遍历），
那类改动的收益在毫秒级、能压过噪声。

## 仍然存在的真实开销（架构级，值得做）

1. **AI 占 tick CPU 的 94.2%**（2.81 ms vs 关掉 AI 后 0.16 ms）。任何 tick 优化
   都应该从 AI 入手，而不是快照编码或 loot 管理。
2. **`thinkBot` 自身 15.9% 自耗时**：900+ 行单函数，每帧对全部存活 bot 调用。
   「计时器递减 + 卡住检测 + 各种 if 分支」每帧全跑。
3. **`findPath` 7.4%**：同队 bot 常去同一区域，可按 (起点格, 终点格) 做短 TTL 路径缓存 ——
   这是真正的架构级优化，收益可压过噪声。
4. **`sanitizeInput` 2.5%**：bot 输入也要经过完整白名单校验。但这是**安全网**
   （防未来 AI 代码写出非法值），不建议拆。

## 仍然存在的真实开销（下一步可做）

1. **`thinkBot` 自身 15.9%**：它是 900+ 行的单函数，每帧对全部存活 bot 调用。
   认知决策内部有 `nextThink` 节流，但「计时器递减 + 卡住检测 + 各种 if 分支」
   仍然每帧全跑。可以把「反应类决策」也做成分帧：bot 的 `think` 按 2–3 帧一轮，
   未轮到的帧只复用上次的输入。
2. **`findPath` 7.4%**：A\* 虽然有 scratch 复用，但没有「多 bot 共享路径」的机会。
   同队 bot 常去同一区域，可以按 (起点格, 终点格) 做短 TTL 的路径缓存。
3. **`sanitizeInput` 2.5%**：bot 的输入也要经过一次完整白名单校验（`botInput` →
   `sanitizeInput` → `input`）。bot 是服务端自己生成的，可以走一条「可信输入」快路径。
